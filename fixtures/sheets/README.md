# `fixtures/sheets/` — drawing-set golden corpus

**Status: populated for SVG, dimension chains, area statements and DXF *structure*.
The `.dxf` files themselves are deliberately not committed — they are written and
audited on every run instead; see "The `.dxf` files" below.**

Playbook §7 specifies the sheet engine and §16 the golden-file strategy. Phase 8 is
described in SKILL.md as "the moat", and this directory is where the moat is measured.

Generate / verify:

```bash
python3 fixtures/sheets/_tools/generate_inputs.py          # the input op logs
python3 scripts/sheet_goldens.py                           # check (exit 1 on any diff)
python3 scripts/sheet_goldens.py --regen                   # regenerate, deliberately
python3 scripts/sheet_goldens.py --list                    # what the corpus contains
python3 scripts/sheet_goldens.py --pdf                     # also drive the PDF path
```

Neither command needs a single third-party package. That is the point: the SVG renderer,
the dimension arithmetic, the schedules and the area statement are pure integer code, so
this gate runs on a bare Python 3.9 as well as in CI.

## What is here

| File | Content | How it is compared |
|---|---|---|
| `inputs/*.json` | **op logs** + the folded result they produce | regenerated by `_tools/generate_inputs.py --check` |
| `<project>-<sheet>.svg` | the rendered sheet, print-true A2 | **byte-diff** after normalisation |
| `dims-<project>.json` | every dimension chain, with `sumMm` recorded next to `overallMm` | byte-diff |
| `areas-<project>.json` | the area statement, integer mm² throughout | byte-diff |
| `dxf-<project>.json` | the DXF **structure**: entity counts per layer, layers used, dimension-segment count, and per hatch the ACAD pattern name + scale + angle | byte-diff |
| `index.json` | manifest: project → sheets, state hash, chain count, provenance | byte-diff |
| `<project>.dxf` | the DXF export | **written + `ezdxf.audit()` every run, bytes not committed — see below** |

Two invariants that used to be implementations waiting for data now have data:
`services.drawings.dimensions.assert_chains_sum` (a chain must sum to its overall
dimension exactly — the reason lengths are integer mm and never floats) and
`find_label_collisions`. Both are asserted over the whole corpus, and both are
assertions, not metrics: the harness exits 1 on a chain that does not add up or on a
single overlapping pair of text labels.

## Why the inputs are op logs

`fixtures/plans/README.md` argues this at length and it applies verbatim: room ids are
history-dependent, so a geometry snapshot pins the accident of construction order, and a
snapshot cannot be replayed. So `inputs/*.json` are op logs, folded through the real
`garh_model` engine by the harness. Every room, area, id, slab and state hash in a golden
is *derived by production code*, not typed in by hand.

The two models:

- **`demo-01-two-room`** — `garh_model.testing`'s two-room fixture, op for op. Shared with
  the model core's own goldens, so a change in the fold shows up in both places at once.
- **`demo-02-blr-30x40-g1`** — §17's demo project geometry: 30×40 ft Bengaluru plot, 9 m
  road south, G+1, four rooms per floor, a dogleg stair, `blr` rule pack. Setbacks are
  real numbers (front 3000, sides 1000, rear 1500 mm), which is what gives the site plan's
  setback chains and the area statement's setback rows something true to print.

`demo-02` is **hand-drawn, not solver output**, and is labelled as such in its own
`provenance` field. `fixtures/plans/` — the solver's corpus — is still empty until Phase 3,
and a fabricated solver golden would be worse than none. `scripts/sheet_goldens.py`
switches to `fixtures/plans/` automatically the moment it has content
(`discover_inputs()`); the goldens get regenerated in that same commit, with a note.

## Why SVG is byte-compared but DXF is not

SVG output is deterministic by construction — no timestamps, no generated ids, no
order-dependent attributes, integer-derived fixed-point coordinates — and it is also the
§13 sanitisation surface (no `<script>`, no `<foreignObject>`), so a byte diff is both a
regression test and a security test. DXF carries `$TDCREATE` and a handle sequence;
comparing bytes would fail on every run and teach the team to ignore the gate. DXF is
therefore compared **structurally**, via `dxf-*.json`.

## The `.dxf` files: audited every run, bytes never committed

`ezdxf` is now installed wherever this corpus runs, so every project's DXF **is**
produced on every run: `scripts/sheet_goldens.py` calls
`services.drawings.export.dxf.write_dxf_bytes`, which runs `ezdxf.audit()` and refuses
to save a document that fails it, then discards the bytes. A DXF that fails §16's
"opens clean" check therefore fails the gate, on every run, without a golden.

The bytes are still not committed, and the section above turned out to be exactly
right about why — confirmed the hard way. A byte golden was built, committed, and then
**failed two runs in three against a golden the first run had just written**: ezdxf
assigns entity handles from a counter that is not reproducible across processes, so the
handles and the OBJECTS ordering move between runs. Normalising the five per-save values
(`$TDCREATE`, the two GUIDs, two `<version> @ <timestamp>` stamps) is not enough, and
normalising the handle sequence as well would mean rewriting most of the file — at
which point the golden pins little more than the JSON already does. A gate that fails at
random is worse than no gate: it teaches everyone to ignore it. So the byte golden was
removed again.

What the bytes would have caught is pinned instead, deterministically, in
`dxf-*.json`: **per hatch, the ACAD pattern name and the scale and angle passed to
`set_pattern_fill`.** That is not decoration. Entity counts alone cannot tell brick from
concrete, nor a hatch drawn at 45° from the same hatch drawn at 90°, and this exporter
shipped three such defects — `earth` rendered as `cross`, hatches 31× too dense, and the
authored angle added to the pattern's own — while the count-only golden stayed green
through all of them. Reintroduce any one of the three today and `dxf-*.json` goes red.

## What is normalised before diffing

Exactly this, and nothing else:

- **SVG** — CRLF/CR → LF; trailing whitespace stripped per line; exactly one final
  newline (`services.drawings.render.svg.normalize_svg`).
- **JSON** — `sort_keys=True`, two-space indent, ASCII, one final newline.

No id rewriting, no timestamp stripping, no attribute sorting. The renderer emits nothing
volatile in the first place, so there is nothing to launder — and a normaliser that erased
ids would also erase a real regression in which every id changed.

## The hand-checked reference set is EMPTY, on purpose

F7-A's launch gate is *"≥90% dims accepted unedited"*, measured against sheets **an
architect has read**. That cannot be generated. `index.json` therefore carries
`handChecked: false` on every project and an explicit `handCheckedReferenceSet.status:
EMPTY`. Marking any file here as hand-checked would fake the launch gate, which is the
precise failure golden rule 10 exists to prevent.

## Rule for whoever changes a renderer

Regenerating a golden is a deliberate act with a note in the same commit (golden rule 10).
`--regen` exists so that is one command; the note is the part that cannot be automated.
